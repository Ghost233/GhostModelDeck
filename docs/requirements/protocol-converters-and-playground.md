# 命名 JEV 模型路由、标准协议与应用内推理测试场

日期：2026-10-07（Asia/Shanghai）。状态：已确认、待实施；已整合命名委员会与原生模型直连需求。规范工单：[命名 JEV 模型路由、标准协议与应用内推理测试场规格](https://github.com/Ghost233/GhostModelDeck/issues/32)。本文按 to-spec 模板整理，沿用已确认的需求与测试接缝，不表示功能已实现或验收通过。

领域词汇见 [领域记录](../../CONTEXT.md)，架构决定见 [ADR 0001](../adr/0001-virtual-jev-protocol-boundary.md) 与 [ADR 0002](../adr/0002-named-council-model-routing.md)。

## 问题陈述

我已经完成本地 JEV 委员会能力，希望把它接入 Hermes 等客户端，并在 GhostModelDeck 内直接检查 JEV 模型及委员会的输入输出。当前委员会对外返回每席意见、综合评分、分歧和故障组成的自有结构，标准 Jev 客户端不能直接消费；应用对部分输入类型的限制也比原生 JEV 契约更严格。

现有软件内咨询界面主要面向 JEV 单题，缺少覆盖当前受支持 JEV 模型的推理测试场。我难以在同一处核对实际发送请求、JEV 原始响应、委员会咨询结果和客户端收到的转换结果，接入问题需要到软件之外排查。

当前只有一份全局委员会席位选择，不能保存 quick、hard 等不同模式，也不能让客户端按模型名在委员会与原生单模型之间选择。运行实例的随机 alias 和模型库显示名称不能直接作为稳定、唯一的调用名称；重启、切换配置及修改席位后，我需要能对账本次请求实际使用的来源。

## 解决方案

将委员会作为虚拟 JEV 引擎，通过 GhostModelDeck 自有协议转换器提供标准 Jev typed HTTP 与 MCP 结果。允许在软件内保存多个委员会模型及其独立席位、模型绑定与超时，例如 quick、hard；客户端显式指定 model 选择对应配置，也可以指定原生模型的固定调用名，直接调用本机 JEV 并跳过委员会聚合。

两类模型共用稳定、唯一的调用名称。默认输出采用标准 JEV 结构，完整委员会咨询结果只在单次显式开启 debug 时附带；原生直连保留引擎实际决策字段与用量。配置可以在模型尚未就绪时保存，实际推理继续检查 Ready、能力与唯一实例，不隐式加载模型。

增加应用内 JEV 推理测试场，支持表单和完整 JSON 编辑，复用已经 Ready 的 JEV 推理实例。原生模式检查 JEV 的实际输入输出；Jev HTTP 与 MCP 模式按调用模型名实际经过对应本机入口，检查模型解析、请求校验、委员会或原生调用、转换和协议返回的完整链路。软件与客户端可以发现当前可调用模型及来源类型。

本期输出转换覆盖 Jev typed HTTP 与 MCP，测试场和专项验收仅聚焦 JEV。llama.cpp 标准文本模型、oMLX 和标准文本 SSE 测试移出本期；承载 JEV 决策能力所需的现有引擎调用与资源控制仍在 JEV 链路内。OpenAI Chat 输出转换留待后续。

## 实现决策

1. 扩展命名模型与委员会配置管理、原生决策协议的输入与结果校验、委员会业务控制、统一协议转换器、HTTP/MCP 协议适配及推理测试场。桌面、HTTP、MCP 与既有业务继续共用同一应用运行图和实际推理实例；委员会核心保持纯 Dart，界面与协议适配不维护第二套计算或模型运行逻辑。

2. Jev typed HTTP 提供 POST /v1/systemone。MCP 单题与批量工具改为 decide_jev 与 decide_jev_batch，通过必填 model 选择委员会或原生模型，正常业务结果使用标准 JEV 结构。项目尚未上线，替换 consult_jev_council 与 consult_jev_council_batch，不保留平行旧名称或旧输出协议工具，并同步工具发现与软件生成的连接配置。MCP 协议外壳保持 MCP 规范，文本 JSON 与 structuredContent 表达同一业务结果。

3. 正常成功结果的顶层为 model、answers、usage。answers 按请求中的问题 ID 返回；choice 答案包含 type、choice、probabilities、confidence，score 答案包含 type、score、legend、probabilities、confidence，noul 答案包含 type、noul。默认不附完整席位、综合、分歧与故障组成的委员会自有结构。

4. 委员会模型与原生 JEV 模型使用用户设置的固定调用名，共用全局唯一名称空间；允许 quick、hard 等不带强制前缀的名称，重名明确拒绝，不设隐式优先级。HTTP/MCP 必须显式指定 model，缺少或未知名称明确报错，不保留特殊默认 gmd-council；用户可以创建名为 gmd-council 的普通委员会模型。成功响应的 model 为请求入场时选择的调用名，实际引擎 alias 用于内部身份核对及显式 debug，不把委员会结果标为某成员模型的原始响应。

5. 原生输入兼容先按目标引擎固定版本的推理契约校验，再保留合法内容。应用协议入口要求 model，并对引擎执行必要身份映射；JEV 决策内容具有 state/questions 结构，每题具有 type/instructions 及该题型要求的 criteria：choice 使用非空候选对象，score 使用 2–10 项从低到高的有序数组，noul 的 criteria 可按原生契约省略，提供时使用 false/true 描述对象。

6. state、instructions 和描述保留原生支持的合法 JSON 类型，解除仅因应用当前 String 类型而拒绝原生合法输入的限制。目标引擎支持的扩展字段不静默丢失；缺字段、错误形状、未知题型或不支持输入明确报错，不猜测题型或补造候选。MCP 外壳与 JEV 业务输入分别校验，应用 debug 选项由适配层处理，不混入引擎题目内容。

7. 席位响应须完整有效、绑定到实际模型和运行代次，概率满足既有有限性、范围与归一化校验。任一题缺失或非法，该席整份响应退出所有题目的综合；同一批次的各题使用同一组成功席位，不修补非法结果，也不按题拼接不同成功席位集合。

8. 两席及以上成功时沿用成功席位的等权综合：choice、score 综合有效分布，score 从综合分布计算期望有序索引；noul 对有效标量求均值。只有一席成功时采用该席有效结果，不补造多席综合；零席成功才失败。

9. 委员会 choice、score 的 confidence 按固定原生算法生成，多席时从综合分布计算，noul 不增加 confidence 或虚构概率分布。confidence 表达分布形状，不代表真实正确率、模型独立性或席位一致性。委员会 choice 取最高综合概率候选，概率完全相等时按候选 ID 排序取第一项，完整并列信息供 debug 查看。原生直连保留引擎校验后的决策字段，不采用委员会聚合或并列规则重算原生判断。

10. 委员会 usage.input_tokens 累加参与结果的成功席位实际用量，usage.output_tokens 为 0，不估算未知失败用量。统计保留引擎返回口径，不把多个席位的用量表示为去重后的单模型输入长度。原生直连保留该引擎返回的实际 usage，不进行多席求和。

11. 整轮超时使用停止前已完成的有效席位，至少一席成功即可正常返回，零席成功返回错误。请求尚未返回时主动取消以已取消结束，不再产生正常成功输出，已收到的证据可供 debug 查看。晚到结果不得改变已结束调用、恢复失效代次或污染并发与后续调用。

12. debug 默认关闭，软件、HTTP、MCP 均支持单次显式开启。关闭时正常成功结果严格采用标准结构；开启时保留标准字段并额外附带 debug 扩展，关联同一实际调用，展示选定来源与配置快照、实际发送请求、原始响应、转换结果及耗时。委员会路径额外提供每席状态/错误、有效席位与完整委员会咨询结果；原生路径保留实际单模型证据，不伪造委员会结果。配置的 API key、Authorization、Cookie 等认证凭据不进入调试展示。

13. 非法 JSON/输入、缺少 model、未知模型、未就绪、实例歧义、能力不匹配、引擎错误、零成功、超时和取消明确区分。HTTP 使用 JEV error 结构与对应错误状态；MCP 使用同一业务错误数据及 isError，传输与 JSON-RPC 错误按 MCP 协议处理。错误不包含伪造的成功 answers；显式 debug 可附已完成证据。

14. 推理测试场仅选择已 Ready 且具有相应 JEV 决策能力的实例；启动、停止仍由现有模型库负责，不因提交测试而启动进程、加载或换模型。按模型能力筛选，不因承载 JEV 的引擎属于 llama.cpp 兼容系列而排除 JEV 调用；推理入口不开放引擎管理接口。

15. 表单与 JSON 编辑同一份待提交请求，表单负责常用字段，JSON 可以表达完整输入。复杂值通过 JSON 编辑，切换不静默删除标准或扩展字段，提交前可查看实际将发送的请求；表单和 JSON 经过同样的协议校验。

16. 测试场覆盖当前支持的 JEV 决策能力。原生模式通过现有受管业务入口检查同一 JEV 实例的实际输入输出；Jev HTTP/MCP 模式按调用名实际访问对应本机协议入口，验证模型解析、请求校验、所选委员会或原生调用、转换与协议返回，不用格式预览代替协议往返。JEV typed 保持非流式，不新增标准文本或 SSE 测试功能。

17. 本次状态、错误、取消和输出与本次调用关联，不把上一次成功结果作为本次成功。JSON 可选择、复制。debug 只用于本次请求与软件中的本次结果查看，不自动写入磁盘或建立历史库。

18. 沿用应用既有资源上限、整轮预算、请求入场与取消/停止控制，并明确这些是应用限制。连接、订阅和许可有归属及释放入口，测试场与协议调用不创建推理实例副本或干扰其他调用及驻留实例。

19. 软件内可以创建、编辑、重命名和删除多份委员会配置并持久保存；每个委员会模型关联一份独立配置，字段包括调用名、席位/模型绑定和整轮超时。所有配置保留统一的等权综合及至少一席完整成功规则，不增加配置专属权重、聚合算法或成功门槛。quick、hard 是用户定义的名称，不表示应用会自动判断难度或预置席位。

20. 委员会席位持久绑定稳定模型资产与引擎组合，运行时解析对应 Ready 实例；不保存随机实例 alias，不自动加载。不可用、实例歧义或所需题型能力不匹配的席位明确失败，不任选实例；其他席位存在整批完整成功结果时仍可返回。原生直连解析绑定模型的唯一可用受管实例，不可用、歧义或能力不匹配时直接返回对应错误。

21. 允许为本机已登记但尚未 Ready 的 JEV 模型设置固定调用名和委员会席位，软件明确展示未就绪及不可用原因，配置操作不触发加载。配置与可调用状态分开，实际推理必须符合本次题型能力、Ready、模型身份与运行代次约束。重复席位拒绝、正超时预算及既有资源上限继续适用。

22. 请求入场时固定调用名、输入、模型绑定和委员会配置快照。后续编辑、重命名或删除不改变已经开始的请求，也不因此取消它；后续请求使用保存后的新配置，旧名在重命名或删除后不接收新调用，不建立隐藏别名。主动取消、模型停止及代次失效仍按既有生命周期处理。

23. 原生直连复用既有受管单模型入口与同一实际实例，校验原生响应后保留 choice、score、noul、概率、legend、confidence 和 usage，只进行必要的公开 model 身份映射；不通过委员会综合、不重算原生决策，也不因现有结果 DTO 的字段限制丢失 confidence。

24. 软件显示所有已配置委员会及原生调用名与可用状态；HTTP 模型列表与 MCP 模型发现提供当前可调用的 JEV 来源并区分类型。列表按模型绑定可用性判断，不把“存在某个 Ready 实例”等同于“路由唯一且可调用”；发现不保证任意题型均支持，本次提交仍校验题型能力。既有标准文本模型发现继续遵循其已定契约。

## 测试决策

1. 测试接缝沿用已经确认的最高层级应用业务入口和同一运行图。功能用例经过真实业务控制及协议转换；HTTP/MCP 用真实本机请求与响应驱动，原生测试通过现有受管入口驱动。优先复用已有接缝；如完整原生请求需要扩展接口，应扩展生产业务入口，不增加测试专用业务接口。

2. 仅在外部引擎进程/HTTP、文件和必要平台连接等 I/O 边界使用可控替身；不替代委员会、协议转换器或资源管理业务，不访问私有方法，不按内部步骤逐行建立测试。断言公开输入输出、状态、资源变化与错误。

3. 可借鉴现有的委员会批量有效性与部分失败测试、整轮截止/取消/晚到及并发隔离测试、MCP 工具发现与文本/结构化一致测试、原生 JEV 决策协议负例及 JEV 实例生命周期/停止排空测试。新增用例复用这些公开驱动与外部 I/O 替身边界。

4. 验证原生合法的文本与 JSON 类型、混合题型、原生支持的扩展字段及实际模型绑定。覆盖缺字段、错误 questions/criteria 形状、未知题型、能力不匹配与未 Ready；确认明确拒绝且不隐式加载、不静默删字段。

5. 以独立已知向量核对等权分布、choice 单值与完全相等的并列规则、score 期望索引、noul 标量、原生 confidence 和实际用量求和。包含席位意见相反的样例，区分对综合分布重新计算 confidence 与平均成员 confidence；不复刻实现作为测试判定依据。

6. 覆盖全成功、部分成功、单席、零席，以及某席任一题缺失或非法时整席退出综合。相同决策通过 HTTP/MCP 返回同一标准业务结果；MCP 文本 JSON 与 structuredContent 相等，默认不包含完整委员会自有结构。

7. 使用可控时序覆盖“一席已完成后主动取消”和“一席已完成后超时”，分别验证取消结束与有效结果返回。覆盖晚到封存、其他并发调用不受影响、停止排空与许可回收；不依靠偶然计时、测试数量或杀掉驻留实例证明正确。

8. 覆盖软件、HTTP、MCP 的 debug 默认关闭与本次显式开启；开启后逐项核对来源、配置快照、真实请求、原始结果、转换结果、故障和耗时。委员会核对每席及完整总结果，原生直连核对单模型证据且不伪造委员会结果；确认认证凭据未进入展示，错误与取消不会误用上次结果。

9. 驱动实际测试场验证 Ready JEV 实例及命名来源选择、表单/JSON 编辑与切换、复杂字段保留、混合批量、JEV 原生非流式请求、HTTP/MCP 实际往返、错误/取消与复制结果；分别覆盖 quick/hard 等委员会及原生固定调用名，确认复用实例而非另建模型运行。

10. 执行与改动相关的格式、静态分析和自动化行为检查。真实引擎/模型及 Hermes 等客户端联调单独记录实际证据；schema 校验、替身测试与构建不能代替真实推理、概率质量或实际客户端接入结论，不继承旧阶段证据作为新增接口通过证明。

11. 通过软件及同一公开业务入口创建不同席位与超时的 quick/hard，核对保存、重启恢复、编辑、重命名、删除、名称冲突和不可用状态；离线绑定保存不产生启动/加载副作用，模型就绪后按稳定绑定恢复可用。

12. 通过真实 HTTP/MCP 验证必填 model、名称路由、原生直连与委员会区分，以及单题/混合批量。以引擎已知原生响应核对直接路径的决策字段、confidence 与实际用量完整保留，除公开 model 映射外不重新综合，也不产生其他席位调用。

13. 使用可控时序在请求执行期间修改、重命名或删除配置，核对该请求仍使用旧名称、输入、成员与超时快照，新请求使用新配置或明确拒绝旧名。验证不同配置的并发、超时、取消和晚到隔离，不靠偶然时间证明快照一致性。

14. 核对软件模型状态、HTTP/MCP 发现、唯一实例准入及本次题型验证的一致性；包含某席离线但其他席完整成功、同一绑定多实例歧义及部分题型不支持。MCP 发现使用新工具名，单题/批量 schema 必填 model，软件生成的连接配置可使用决策与模型发现能力。
