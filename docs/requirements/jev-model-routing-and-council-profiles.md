# 命名委员会配置与 JEV 模型路由补充需求

日期：2026-10-07（Asia/Shanghai）。状态：Q15–Q25 与 Q26 整体需求均已确认，规范规格及相关 GitHub 工单已同步并读回核验；未开始实现。规范工单：[命名 JEV 模型路由、标准协议与应用内推理测试场规格](https://github.com/Ghost233/GhostModelDeck/issues/32)。

## 用户明确提出的方向

- 可以配置多个委员会模型，例如 quick、hard，每个模型标识对应不同的委员会配置。
- 请求指定委员会模型时使用该配置执行委员会咨询。
- 请求直接指定上游 JEV 模型名时，不走委员会模式，而是调用该原生 JEV 模型。
- 既有标准 JEV 输出、原生输入兼容、debug 和 JEV-only 范围作为已确认基线；新增路由对固定 model 身份的影响需同步。

## 与既有决策的关系

原规格与 ADR 0001 使用固定 gmd-council 标识和单份委员会。此次决定扩展为多个命名委员会模型，以及原生 JEV 单模型路由。两类模型的调用名称全局唯一且稳定；HTTP/MCP 必须显式指定 model，不保留特殊默认 gmd-council 路由。用户可以创建同名普通委员会模型。已将此次决定整合进规范规格并更新 ADR，旧固定标识不再作为当前规范契约。

新方向的架构背景见 [ADR 0002](../adr/0002-named-council-model-routing.md)。原有的概率综合、单席/零席处理、取消和 debug 决策不因命名自动改变。

## 当前实现事实

- 现有委员会只有一份全局席位集合，GUI 与 MCP 共用；没有命名配置或委员会配置持久化。启动模型集合是另一概念，不代表委员会配置。
- 现有公开模型标识是 gmd 加资产 ID，资产显示名称不是路由键；JEV 后端每次启动会生成随机 model_alias，不能把它当成跨启动稳定的用户模型名。
- 原生单模型 JEV 调用已有独立入口，可复用模型身份/代次核对、能力准入、活动请求、取消与排空，无须先包装成委员会。
- 当前 MCP 工具未接收 model，公共 HTTP 尚无 JEV 路由；新增的名称分派属于待实施能力。
- 当前 MCP 不接受调用方 timeout/deadline，采用 10 秒整轮预算；现有内部原生调用同样默认 10 秒。配置超时属于新增的委员会配置字段，不要求扩展调用方超时覆盖。
- 当前席位选择拒绝重复的同一席位 ID；新选择的不可用席位会导致选择失败，已选席位暂时不可用则可保留。咨询时未就绪或题型能力不匹配按单席失败处理。
- 当前模型发现与唯一可调用判定并不一致：存在多个 Ready 实例的资产仍可能出现在列表中，但调用会报歧义；Ready 也不保证所有 JEV 题型均已验证。新增发现应按新绑定的可调用状态判定，实际请求继续检查所需题型能力。
- 单模型解析保留引擎计算的 choice、score、noul 和完整 rawResponse，但当前 DTO 的 toJson 会舍弃原生 choice/score confidence。原生直连的标准输出需保留校验后的原生决策字段与用量，除公开 model 身份外，不借用委员会聚合重算单模型判断，也不因现有 DTO 限制丢失 confidence。

事实依据已只读核对；没有执行推理或修改服务、客户端配置。

## 已确认决定

用户回答 Q15 A、Q16 A、Q17 A、Q18 A：

- Q15：每份配置允许选择席位、绑定模型及设置整轮超时。沿用等权综合与至少一席完整成功即可返回的规则，不增加按配置调整权重、聚合算法或成功门槛。
- Q16：在软件内创建、编辑、删除委员会配置，持久保存，重启后保留。
- Q17：本期原生模型直连只覆盖本机已登记且 Ready 的 JEV 模型，不增加远程 JEV 服务。
- Q18：委员会模型和原生模型共用全局唯一的调用名称空间；quick、hard 可以直接使用。重名明确拒绝，不采用隐式优先级或强制委员会前缀。

用户回答 Q19 A、Q20 A、Q21 A、Q22 A、Q23 A：

- Q19：用户为原生模型设置固定调用名并绑定具体模型，允许采用上游模型名或为量化变体设置不同名称。成功响应的 model 使用该调用名，实际引擎 alias 留作内部绑定与显式 debug 证据。
- Q20：HTTP/MCP 都要求显式 model，不保留特殊默认路由。缺少 model 明确报错；gmd-council 可作为用户创建的普通委员会模型名。
- Q21：持久席位绑定稳定的模型资产与引擎组合，调用时解析其 Ready 实例。不保存随机实例 alias，也不自动加载。不可用或匹配多个可用实例的席位明确失败，不任选实例；其他席位存在完整成功结果仍可返回。
- Q22：请求入场时固定调用名、输入及委员会配置快照。已开始请求继续使用旧快照；后续请求使用已保存的新配置。重命名或删除后，旧名不接受新调用，已开始请求不会因此被取消。
- Q23：软件显示所有已配置模型及可用状态；HTTP 模型列表和 MCP 模型发现提供当前可调用的委员会与原生 JEV 名称，并区分来源类型。

用户回答 Q24 A、Q25 A：

- Q24：将现有 consult_jev_council / consult_jev_council_batch 替换为 decide_jev / decide_jev_batch，按必填 model 选择委员会或原生模型；同步工具发现及软件生成的连接配置，不保留平行旧名称工具。
- Q25：允许为本机已登记但尚未 Ready 的 JEV 模型设置调用名与委员会席位。界面明确展示未就绪，配置操作不启动或加载模型；实际调用仍要求 Ready 且能力匹配。

原有的不隐式加载、完整席位校验、取消、超时与 debug 规则仍是基线。quick、hard 是用户定义的名称，不表示应用会自动判断请求难度。

## 完整调用行为

| 请求 model | 决策来源 | 标准结果 |
| --- | --- | --- |
| quick | 名为 quick 的委员会模型对应的配置 | 该配置成功席位的标准 JEV 综合结果 |
| hard | 名为 hard 的委员会模型对应的配置 | 该配置成功席位的标准 JEV 综合结果 |
| 用户设置的原生调用名 | 绑定的本机原生 JEV 模型 | 该模型校验后的原生决策结果，不经过委员会聚合 |

以上名称为示例，不预置 quick/hard 的成员或难度策略。两类成功响应的 model 均为请求入场时选定的调用名，常规结构为 model/answers/usage；显式 debug 关联实际路由、发送请求、原生响应及本次证据，委员会路径额外含完整委员会总结果。原生路径保留原生判断与用量，不伪造委员会结果。

HTTP 使用 POST /v1/systemone；MCP 单题与批量决策使用 decide_jev / decide_jev_batch。两种协议执行相同的模型解析、输入校验与运行约束，外部请求不能省略 model、隐式使用全局委员会或要求模型自动启动。软件测试场可以选择同一套命名来源，HTTP/MCP 模式实际经过本机入口。

配置与可用性分开：离线配置可以保存，只有满足本次题型及 Ready/唯一实例条件的来源才能推理。委员会中的不可用、歧义或题型不匹配席位明确失败，至少一个席位整批完整成功即可返回；原生单模型不可用、歧义或能力不匹配直接返回对应错误。已有的输入上限、重复席位拒绝、正超时预算和生命周期约束继续适用。

配置重命名与删除只影响后续请求；旧名不接受新调用，不建立隐藏别名。已经执行的请求使用入场快照完成，原有主动取消、超时使用已完成结果、晚到隔离和资源排空规则不变。

## 新增验收行为

- 在软件内创建 quick/hard，保存不同的席位与超时；重启应用后配置及调用名恢复，同一请求按 model 路由到对应配置。
- 原生调用名复用既有受管实例，保持原生 choice/score/noul、概率、confidence 与用量，响应 model 为调用名，显式 debug 能核对实际引擎身份。
- 通过真实 HTTP/MCP 入口核对缺少 model、未知名称、名称冲突、未就绪、实例歧义和题型不匹配；委员会部分失败不影响其他完整成功席位，零成功明确失败。
- 对正在执行的请求修改、重命名或删除配置，核对该请求继续使用旧名称与旧配置，后续请求使用新配置或明确拒绝旧名。
- 保存离线模型绑定时不产生加载或启动副作用；软件显示不可用原因，模型就绪后按稳定绑定重新可用；发现结果反映可调用状态及来源类型。
- 核对 MCP 新工具名、必填 model、单题/批量、发现与连接配置一致；测试场实际经过所选协议，默认与显式 debug 保持既有结果边界。

验证继续沿用已确认的同一应用运行图、公开业务入口和真实本机 HTTP/MCP 往返，仅在外部 I/O 使用替身。本期仍专注 JEV，不增加标准文本 llama.cpp/oMLX 与 SSE 验收。
