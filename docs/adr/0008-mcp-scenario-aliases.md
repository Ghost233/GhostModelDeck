# 场景显示名称与模型名字分开，HTTP 和 MCP 共用模型名字

用户希望 MCP 客户端通过场景选择后台实例或委员会，初始提供短／长与视觉／非视觉的四类定义，场景及名称可编辑。
Q7 明确暂时固定这四个场景槽位，目的是稳定给 LLM 的 MCP 提示词结构，不提供新增或删除槽位。
Q27 确认首次预建并启用四个场景，默认显示名称可修改；模型名字与绑定由用户自行配置，未配置或没有可用实例时不列入 MCP 模型列表。
场景显示名称与模型名字分开，模型名字可作为实际实例或委员会的虚拟模型名字，并通过后台绑定路由。MCP 默认列表仅展示启用且运行可用的场景模型。
Q12 明确例如显示“4k上线+视觉”，模型名字为 `fast-v`，再由后台绑定选择实际实例或委员会。
Q13 明确 HTTP 与 MCP 共用模型名字，可调用实际模型或用户定义的虚拟模型；不采用两种入口分别命名或 MCP 仅允许场景名字的建议。
Q14 确认 HTTP `/v1/models` 列出全部可用的实际实例、委员会及场景虚拟模型；MCP 默认列表仅列四个场景中已启用且可用的模型，已知有效模型名字仍可直接调用。
这会收敛默认 MCP 发现列表，能稳定客户端调用，也会增加场景绑定配置与可用性规则；实际调用统一使用 `model` 选择模型名字。

Q1 确认四类场景用于结构化判断，普通聊天仍通过 HTTP／测试场使用。Q15 修正视觉场景的含义：仅为用户定义的说明，不据此新增图片协议、能力检测、成员筛选或视觉专用流程；按用户选定的绑定调用。
Q2 保留委员会至少一名成员可用即可被发现的规则，不要求全部成员就绪。
Q3 明确上下文来自绑定实例，委员会取成员容量的最小值；固定 4096／32768 及固定四个调用名的方案不采用。
Q4 的实际容量经 Q6 澄清为实例保存的有效上下文配置，不能以模型声明的理论上限代替，也不要求先启动观测。
Q5 确认委员会按全部成员取最小容量并固定，成员启停只影响可用性，不改变对外容量。
Q8 确认 MCP 提示词采用固定模板结合当前场景配置自动生成，客户端重连或刷新取得最新内容。
Q9、Q10 确认参数编辑时预览容量变化，取消不保存，也不自动重启实例。
Q11 修正生效时机：新参数重启实例后才生效；保存只更新待应用配置与预览，重启应用后再更新关联委员会与场景的有效容量。
容量按实例配置可直接确定；调用时的可用性复核、失败和 partial 返回沿用现有行为。用户已于 2026-10-16 整体确认 Q1～Q27。
